# Feature Specification Document — PLAY-191: הקובץ qa/s7_stop.txt

## 1. Feature Overview

- **מה בונים:** קובץ טקסט חדש, `qa/s7_stop.txt`, בתיקייה `qa/` הקיימת בשורש המאגר. הקובץ מכיל שורה אחת בלבד: `stop and retry`.
- **הבעיה:** בודקי ה-QA צריכים סיפור קטן וצפוי כדי להפעיל עליו את פקדי העצירה והניסיון החוזר (stop / retry) של מפעל הפיתוח. התוצר הזה פשוט, ולכן קל לבדוק אם ריצה שנעצרה ונוסתה מחדש מסרה בדיוק אותו דבר (כותרת הסיפור ותיאורו, PLAY-191).
- **משתמשים:** בודק QA שמפעיל את מפעל הפיתוח. נקודת המגע היחידה היא תוכן הקובץ בענף העבודה ובבקשת המיזוג.

## 2. Goals & Non-Goals

### Goals

- הקובץ `qa/s7_stop.txt` קיים בתיקייה `qa/` שבשורש המאגר.
- הקובץ מכיל שורה אחת בדיוק: `stop and retry`.
- התוצאה פשוטה מספיק כדי לבדוק בעין, אחרי עצירה וניסיון חוזר, שהריצה מסרה בדיוק את הקובץ הזה.

### Non-Goals

- כל שינוי בקובץ אחר במאגר: קוד תחת `src/`, בדיקות תחת `tests/`, סקריפטים קיימים תחת `qa/`, ה-CI ותצורת `.factory/`.
- בדיקות אוטומטיות חדשות. לפי הסיפור, אין צורך בבדיקות מעבר לבדיקת תוכן הקובץ.
- תיעוד, רישום ב-CHANGELOG או כל שימוש בקובץ מתוך קוד אחר.
- פקדי העצירה והניסיון החוזר עצמם: הסיפור רק מספק להם תוצר לבדיקה, ואינו משנה אותם.

## 3. Functional Requirements

- **FR1 — מיקום:** קובץ חדש בנתיב `qa/s7_stop.txt`, יחסית לשורש המאגר. התיקייה `qa/` כבר קיימת וכוללת היום את `qa/s3-a.sh`, `qa/s3-hello.sh`, `qa/20261109-s1/` ו-`qa/20261110-s3/`.
- **FR2 — תוכן:** הקובץ מכיל שורה אחת בדיוק, והטקסט שלה הוא `stop and retry`: אותיות קטנות, רווח אחד בין המילים, בלי מירכאות, בלי רווחים בתחילת השורה או בסופה ובלי שורות נוספות, ריקות או אחרות.
- **FR3 — סוף השורה (הנחה):** השורה מסתיימת בתו שורה חדשה אחד (LF), כמקובל בקובץ טקסט של שורה אחת. אחריו אין תו נוסף. ראו את השאלה הפתוחה בסעיף 8.
- **FR4 — גבול התחום:** זה השינוי היחיד שהסיפור עושה במאגר. כל קובץ קיים נשאר כפי שהוא.
- **FR5 — רגרסיה:** הבדיקות הקיימות (`pytest`, עבודת `test` ב-CI) ושער `gate` נשארים ירוקים. הקובץ החדש אינו מפעיל אותם ואינו נוגע בהם.
- **קלט ופלט:** אין קלט. הפלט הוא הקובץ עצמו בענף העבודה ובבקשת המיזוג.
- **מקרי קצה:** אין התנהגות זמן ריצה. מקרה הקצה היחיד שרלוונטי הוא צורת הקובץ (שורה אחת, ללא שורות ריקות נוספות), והוא מכוסה ב-FR2 וב-FR3.

## 4. User Experience & Behavior

- **מסלול הבודק:** בודק ה-QA מפעיל את הסיפור במפעל, ויכול לעצור את הריצה ולנסות אותה שוב. בסיום הוא פותח את בקשת המיזוג ורואה בה קובץ חדש אחד, `qa/s7_stop.txt`, עם השורה `stop and retry`.
- **מצבים שהבודק רואה:** לפני המסירה הקובץ לא קיים. אחרי המסירה הוא קיים עם התוכן המדויק. ריצה שנעצרה ונוסתה מחדש מוסרת אותו קובץ בדיוק, בלי כפילות ובלי שורות נוספות.
- **מראה ותחושה:** אין. זה קובץ טקסט פשוט, בלי ממשק משתמש.

## 5. Acceptance Criteria

1. The file qa/s7_stop.txt exists in the qa/ folder at the repository root.
2. It contains exactly one line: stop and retry
3. The pull request changes no file in the repository other than qa/s7_stop.txt, except the story's own plan folder stories/PLAY-191/ that the factory commits.

## 6. Dependencies & Constraints (product-level)

- **תלויות:** אין. התיקייה `qa/` כבר קיימת, ואין סיפור אחר שהסיפור הזה נשען עליו.
- **שערי המאגר:** שער הפריסה של play1 (`.factory/plugins/claims-dev/skills/repo-gate/SKILL.md`) בודק שקוד Python נמצא תחת `src/`, שבדיקות נמצאות תחת `tests/`, שסקריפט מעטפת חדש ניתן להרצה ומתחיל ב-shebang, ושאין קובץ גדול מ-200 KB. קובץ טקסט קטן תחת `qa/` עומד בכל הכללים. שער הבדיקות (`.factory/testing.md`: `pytest` בעבודת `test` ב-`.github/workflows/ci.yml`) ושער `CI_FAIL` אינם מושפעים.
- **תיקיית התוכנית:** מפעל הפיתוח מוסיף לאותו ענף את מסמכי הסיפור תחת `stories/PLAY-191/`. אלה מסמכי התהליך ולא שינוי של הסיפור, ולכן קריטריון 3 מחריג אותם.
- **מיזוג:** אדם ממזג את בקשת המיזוג אחרי סקירה. המפעל אינו ממזג.

## 7. Technical Design (deferred to STRUCTURE)

אין כאן עיצוב טכני. השינוי הוא קובץ טקסט אחד, ושלב ה-STRUCTURE יקבע את פירוט העבודה.

## 8. Open Questions

- **סוף השורה (לא חוסם):** "exactly one line" מתפרש כשורה אחת שמסתיימת בתו LF אחד. אם בודק ה-QA משווה את הקובץ בייט-לבייט ל-`stop and retry` בלי תו שורה חדשה בסוף, צריך לומר זאת. *הנחת עבודה:* `stop and retry` ואחריו LF אחד. הסיכון: השוואה בייט-לבייט נכשלת בגלל תו אחד.
